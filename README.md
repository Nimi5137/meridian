# Career workspace — delivery and handoff

This repository is an **incomplete foundation, not a production-ready release**. Product branding is centralized in `src/config/brand.ts`. The existing connected Supabase project named Meridian was used; no new database project or Vercel deployment was created.

## Implemented paths

- Responsive landing page and protected workspace. Supabase email/password registration, verification callbacks, login, logout, password recovery and password update are implemented. Email delivery, OAuth, redirects and production SMTP need configuration and live testing.
- A manually editable profile with version-guarded saves and explicit conflict comparison, plus structured experience, education, project, certification, volunteering, award and publication entries. When concurrent changes occur, the form retains edits and requires explicit confirmation before replacing the current profile; further changes are checked again. Per-field source labels show manual edits, selected reviewed CV suggestions, or unknown for legacy data. Labels are not independent verification. Employment history is never required. Career entries participate in AI drafting and matching and update the profile version.
- Private original PDF/DOCX upload (4 MiB web limit), signed download and text extraction for text-based PDFs and DOCX files. Scanned PDFs/OCR are not supported. Extraction uses the AI gateway and stores a reviewable suggestion, not a silent update. The review shows current and proposed values and applies only checked fields atomically with a profile-version guard. AI output must be checked against the original. The original file is unchanged. Upload checks size, extension and basic signature, but **malware scanning, strong format validation and isolated parsing are not implemented**.
- Stored-job search across titles, companies and locations, source filtering, source-date/last-observed sorting, pagination, job details, saving a job once per user, application status/notes and automatically recorded status activity. The tracker supports search, status filters, pagination and a pipeline grouped only over the current page. Preparation is manually handed off to the original listing. An `applied` status requires a user-recorded submission-evidence note; it is self-reported, not independently verified. Other statuses are user-maintained, not proof of contact. Source records are not continuously verified and may be stale.
- On-demand explainable match analysis of a stored job against the saved profile and entries. Analyses contain a 0–100 fit score, explanations, gaps, eligibility concerns and development opportunities. The score is **not** a probability of an interview or offer. Recent analyses appear in discovery; the system is not yet an automatically ranked global feed. Changing the profile or re-importing the listing marks the analysis stale.
- Application studio: generate text CV and cover-letter drafts, save edited versions, inspect history, download text, DOCX or a plain server-generated PDF, and use browser print/save-as-PDF. Users must verify every statement. Users can enter employer questions and answers, mark sensitive information, explicitly confirm answers, and optionally save or reuse confirmed answers. Copied answers start unconfirmed; editing a confirmed question, answer or sensitivity clears confirmation. Approval is tied to document IDs and a question version; changes invalidate approval. Users can record a self-reported manual submission and evidence note; nothing is submitted automatically. The PDF is a plain, paginated A4 document; its bundled Noto Sans font supports Latin, Greek and Cyrillic text. Unsupported characters, scripts, control characters and documents over 100 pages are rejected rather than silently omitted; use DOCX or browser print in those cases. Review all output before use. Browser print quality varies.
- Interview planning supports manually entered titles, notes and locations tied to an application, with IANA timezones, daylight-saving ambiguity rejection, version-guarded edits and account export. These entries do not send invitations, reminders or calendar updates, and calendar connections do not create them. This feature has mock and rollback-only database tests, not live authenticated browser testing.
- Central AI gateway with HTTP text adapters for Groq, OpenAI, Anthropic and Google Gemini. Models and per-task routing are configurable. AI operations disclose that candidate data is sent to the chosen provider. Requests have a timeout, no redirect following, bounded response bodies, validated provider responses, output validation for extraction/matching and a shared atomic per-user hourly counter. Credentials remain server-side. Provider adapters and workflow validation have **mocked tests only**; no live model was tested. Streaming, tools, vision, embeddings, billing-grade usage accounting, retries, automatic fallback and general provider health monitoring are not implemented; the admin page can run an explicit real text-generation test.
- Greenhouse, Lever, Ashby and SmartRecruiters public-board connector code. Lever and SmartRecruiters pagination is handled; source identifiers are namespaced by board. Imports fail closed on malformed records, repeated pages, changing SmartRecruiters totals and configured page, record and response-size limits; these limits can reject legitimate very large boards. Lever descriptions include available sections, and Ashby HTML is retained when plaintext is absent. SmartRecruiters listing descriptions are currently empty because per-job detail fetching is not implemented. A PostgreSQL-backed ingestion queue supports scheduled due boards, worker leases, idempotent upserts and bounded retries. A separate scheduler must invoke the worker. **No live board was imported or verified in this environment.** There is no expiration detection, cross-source deduplication, incremental sync, distributed rate limiting or production monitoring. Old pre-namespacing imports, if any, must be reconciled before using the new worker.
- Stripe checkout, customer mapping, portal, signed webhook processing, subscription persistence, event deduplication, event-time ordering and a checkout reservation to reduce duplicates. When `BILLING_ENFORCE_AI=true`, AI operations require an active or trialing subscription with a configured price. Prices and tiers come from environment configuration; Stripe displays the actual price at checkout. **All Stripe code is unverified against a real Stripe account.** It is not approved for live charging. Same-second event ordering, operational reconciliation, tax, customer deletion, subscription changes and concurrent/failure edge cases require staging tests and review. If checkout creation fails ambiguously, the reservation remains until it expires; verify Stripe before retrying.
- Optional Google and Microsoft connections implement separate, explicit OAuth consent for read-only Gmail metadata, Outlook basic message details, Google Calendar and Microsoft Calendar events. A user can view up to ten recent message headers or twenty upcoming primary-calendar events; no mail bodies are requested and these results are not stored. OAuth state is one-use and bound to the signed-in user and browser; tokens are encrypted server-side and refreshes use database leases. Disconnect removes stored credentials but **does not revoke provider authorization**; users must remove the app from their provider account to revoke it; doing so may affect other connections to that provider. These paths have mock and rollback database tests only, and have **never been exercised with a real Google or Microsoft account**. Google restricted-scope verification and privacy/security review may be required; Microsoft tenant or publisher consent requirements may also apply.
- AI activity observations record provider, model, task, provider outcome and any reported token counts, without prompt or response text. They are visible in Settings and included in the account export. They are not billing-grade: a signed-in user can call the observation RPCs directly, token data can be missing, recordings can fail or remain pending, provider completion does not establish output validity, and prior calls were not backfilled. Refer to the provider for authoritative usage and charges. A provider call is blocked if quota reservation or tracking is unavailable; if finishing the observation fails after a provider response, the output is retained and the observation may remain pending.
- A JSON export of supported account records, capped at 10,000 total rows and 8 MiB. It uses keyset pagination, but is not a transactional snapshot; concurrent edits can change its contents. Original CV files must be downloaded individually from the profile. Large exports require support; it is not a complete automated portability solution. A staging-only, disabled-by-default account deletion flow exists, but is not production-ready or live-tested; see the deletion runbook below.
- An admin-only readiness page, enabled by an allowlist of authenticated Supabase user IDs, reports configuration presence and missing variable names without exposing values, and displays recent ingestion tasks when service-role credentials are available. Administrators can run a real text-generation test for configured AI providers and see recent outcomes; each test consumes provider usage and the shared hourly limit. Other connection tests are not implemented. A configured status does not establish connectivity.

## Database and security

Thirty-seven SQL migrations in `supabase/migrations` were applied to the connected Meridian project. Their filenames match the migration history. There are 29 public tables, including applications, documents, questions, reusable answers, approvals, submission evidence, profiles, job data, ingestion and billing records. RLS is enabled on all; the `career-documents` storage bucket is private. Users own their profile, documents, matches, applications and billing views; worker/billing mutation operations use the service role. Direct user-written profile, application, import and matching records have database size checks; the newest checks are NOT VALID for existing rows, so legacy oversized records require reconciliation before updating. API roles have no TRUNCATE, TRIGGER, REFERENCES or PostgreSQL 17 MAINTAIN privilege on existing public tables. SQL functions perform application event recording, AI rate limiting, atomic profile review, ingestion queue operations, and billing synchronization/reservations.

Rollback-only database checks verified selected two-user isolation, application uniqueness/event behavior, profile import ownership and concurrency, profile conflict and provenance behavior, career entry behavior, AI request limit, queue claim/retry/token behavior, billing event deduplication/order, checkout reservations, user deletion cascades, question isolation/approval invalidation, AI usage isolation/rate limits/cascade, integration connection isolation/state replay/refresh leases, interview ownership/version guards, direct-write size bounds, and lease-fenced job writes. These checks use rolled-back synthetic records. These are **not** comprehensive RLS, storage or security tests. Service-role access bypasses RLS; protect it as a deployment secret. Avoid logging CV text, tokens or keys. There is no malware scanner or security incident response system.

## Local setup

1. Install Node 22.13 or later in the Node 22 series, run `npm ci`, and copy `.env.example` to `.env.local`.
2. Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to the intended project URL and publishable/anon key. Set `NEXT_PUBLIC_APP_URL` to the externally reachable origin without a trailing slash. Configure the Supabase Auth Site URL, allow the `/auth/callback` redirect, configure production SMTP, and verify confirmation/recovery links. Do not put a service-role key in a public environment variable.
3. For Groq set `AI_DEFAULT_PROVIDER=groq`, `GROQ_API_KEY` and `GROQ_MODEL`. For OpenAI, Anthropic or Google set the selected provider and its corresponding key/model. `AI_DEFAULT_MODEL` is an optional fallback. Task-specific override names are listed in `.env.example`; task-specific models must match their providers. No automatic provider fallback is performed.
4. Run `npm run dev`. For a fresh Supabase project apply `supabase/migrations` in order using the Supabase CLI after linking the intended project. The connected project already has these migrations; do not manually apply them again there.
5. Set `INTEGRATION_ADMIN_USER_IDS` to a comma-separated list of authorized Supabase user UUIDs to expose the configuration-status page in Settings. This is a server-side allowlist, not a complete administrative access-control system.

## Job worker setup

Use only approved employer boards, respecting each provider’s terms and rate limits. Provision `SUPABASE_SERVICE_ROLE_KEY` and `NEXT_PUBLIC_SUPABASE_URL` to a protected worker environment. Register a board with `npm run add-board -- greenhouse BOARD COMPANY` (sources: `greenhouse`, `lever`, `ashby`, `smartrecruiters`). Use a managed external scheduler to invoke `npm run worker:once` at a regular interval, such as every five minutes. Each invocation enqueues due boards, claims up to ten tasks and exits; the database holds retry/lease state. Board intervals are stored in `job_boards`. Monitor failed tasks and worker exit codes. An optional GitHub Actions scheduler definition is included but is disabled by default and has not run here. Partial batch writes can occur before a retry; upserts are idempotent. Scheduled-worker batch writes and completion check the active lease under a task-row lock; load/concurrency and live provider tests remain necessary. The manual import command is an administrative direct-write path outside queue fencing. No jobs are expired automatically.

The optional `.github/workflows/job-ingestion.yml` runs on the default branch every 30 minutes (GitHub schedules may be delayed) and can be dispatched manually. After staging validation and registering approved boards, configure repository secrets `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, then set the repository variable `INGESTION_WORKER_ENABLED` to `true`. Otherwise its job is skipped. The service-role secret is supplied only to the worker step, but anyone who can modify the trusted default-branch workflow can potentially use it: restrict repository access. Configure alerts for failures and verify scheduled runs; GitHub Actions must be enabled, and its scheduler is not a precise timing guarantee. A 20-minute job timeout may interrupt long invocations; unfinished database leases eventually expire and retry. No secrets or repository variable were configured and no schedule has been run in this session.

`npm run import-jobs -- greenhouse BOARD COMPANY` is a manual import alternative. Both scripts require server-side Supabase configuration. Never store service credentials in the repository, browser or shell history.

## Account deletion — disabled by default, staging only

`ACCOUNT_DELETION_ENABLED=false` is the default. The implementation requires a current password, explicit confirmation, and a service-role key. Accounts with verified MFA or without a password must use support; password-only reauthentication is not adequate for MFA. Before deletion, users must disconnect each integration and separately revoke provider access. Any billing customer or checkout reservation blocks deletion, including formerly billed customers. Never bypass this check without reconciling Stripe subscriptions, customer records and retention obligations. The operator must establish a support channel and deletion/retention policy before offering this feature.

Starting deletion durably blocks new CV uploads, checkout and OAuth starts and completions; cleanup enumerates and deletes the user's storage objects, then deletes the auth user and cascaded account records. If interrupted, an existing user may retry; files already removed cannot be restored by retry. A job and a 15-minute lease remain for recovery. If the auth user is already absent, a trusted operator can use `npm run reconcile-deletion -- USER_UUID` with server-side Supabase credentials: it claims the existing deletion job, verifies the auth user is absent, retries storage cleanup, and finalizes the job. It does **not** delete an existing auth user. Monitor unresolved jobs, investigate lease expiry and failures, and treat user identifiers as sensitive. No scheduler or automatic recovery is deployed. Storage limits may require an operator-assisted process.

This is not yet safe to enable for real users: live storage/auth deletion, network failures, concurrent requests, active sessions, MFA, provider revocation, backups, legal retention, billing reconciliation, observability and abuse controls require staging tests and independent security/privacy review. Authentication sessions and signed URLs may remain valid until expiry, and external providers and backups are not erased by this workflow. There is no support workflow or retention schedule implemented here.

## Stripe setup — staging only

Create Stripe recurring prices and set `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, the desired `STRIPE_*_PRICE_ID` variables, `SUPABASE_SERVICE_ROLE_KEY` and `NEXT_PUBLIC_APP_URL`. Register `/api/stripe/webhook` for `checkout.session.completed`, `checkout.session.expired`, `customer.subscription.created`, `customer.subscription.updated` and `customer.subscription.deleted`. Enable and configure the Stripe billing portal. Use test-mode credentials and the Stripe CLI or staging endpoint to verify checkout, retries, cancellation, failed payments, portal actions, signature rejection and reconciliation. `BILLING_ENFORCE_AI=false` leaves AI available subject to its hourly limit; set it to `true` only after price IDs and webhook synchronization have been verified. It fails closed for AI when enforcement is enabled but no qualifying subscription is recorded. No payment has been made or tested here.
