# CV processing security — staging only, not a release approval

The web application's upload action now **fails closed** if a ClamAV `clamd` scanner is unavailable or cannot provide a clean verdict. The extraction action re-scans stored bytes (including legacy documents) and requires a separate parser service; it never falls back to parsing in the web process. `CV_SCANNER_SOCKET` and `CV_PARSER_SOCKET` are absolute Unix socket paths, configured on the server. Without a working scanner, uploads fail; without both services, extraction fails. These are operational prerequisites, not secrets. Original downloads and other non-CV functionality are unchanged.

## Important limitations and release blockers

- The scanner is not installed, configured, deployed, or tested against a real `clamd` instance here. The scanner tests use a simulated INSTREAM socket server, not a live malware engine. Scanners can miss malware, use outdated signatures or fail to inspect embedded/complex content. Test EICAR in a disposable staging environment and alert on failures and stale signatures; never upload real malware or user CVs as a connectivity test.
- Existing Supabase storage policies allow authenticated owners to use Storage APIs directly. The application upload gate is therefore **not an enforcement boundary on direct Storage API access**. Original downloads, signed URLs, existing files and direct Storage API use are not scanned by this change. Preventing bypass requires a reviewed server-only upload/download architecture, policy migration, cleanup of existing objects and comprehensive storage testing. Do not expose this feature to untrusted users as malware-safe.
- The parser service protocol and a synthetic document were tested using a separate local process, **not a sandbox**. The supplied image has not been built or run in a container in this environment. Actual isolation depends on deployment, kernel, runtime, filesystem permissions, image review and resource limits; these have not been independently audited or validated. Never run the parser next to the application with shared credentials, network access, or broad filesystem privileges and call that isolation.
- Unix sockets require co-location or an appropriately protected shared volume; this design is not directly suitable for a standard Vercel serverless function without a different private service architecture. The web app and parser have no configured production deployment. No public launch until isolation, storage bypass, malware handling, abuse tests and independent security/privacy review are complete.

## Parser deployment design to validate in staging

Build `services/cv-parser/Dockerfile` from the repository root after reviewing and pinning the base image and dependency supply chain. Run as the image's unprivileged `node` user with **no secrets, no network, no application data mounts**. Use a dedicated socket directory accessible only to the app and parser's trusted UID/group, with no other host users or containers able to connect. The socket is created mode `0660`; the directory and volume must also have restrictive ownership and mode. Remove only a verified stale socket before restarting the service; it deliberately does not unlink an existing path.

At a minimum use a hardened container profile: read-only root filesystem; all capabilities dropped; no-new-privileges; default or tighter seccomp/AppArmor; `--network none`; bounded writable temporary storage; PID, memory and CPU limits; and an external watchdog with a hard per-job wall-clock limit that can terminate/restart a wedged process. The service handles one document at a time and limits input and response sizes, but its JavaScript timer is **not** a hard CPU limit, and a busy or malformed request can deny service. Protect the socket and apply request concurrency/rate limits before enabling it. Do not log document bytes or extracted text. The parser enforces 4 MiB input, 30 PDF pages, bounded DOCX XML and 40,000 characters of extracted text, but limits are not a sandbox and do not make parsers vulnerability-free.

Run `node --import tsx scripts/cv-parser-service.ts` only inside that isolated deployment with `CV_PARSER_SOCKET` pointing to its socket. The web app must see the same socket path and must not share application secrets with the parser. Validate container restrictions and file/network isolation with adversarial tests and verify restart recovery before use.

## Scanner deployment design to validate in staging

Run a separately managed, restricted `clamd` with current signature updates and an appropriately restricted local Unix socket. Configure its stream and archive limits to cover supported documents; monitor scanner availability, database freshness and scan failures. Set `CV_SCANNER_SOCKET` in the app to that socket. The client uses ClamAV `zINSTREAM`, bounds files to 4 MiB, has a 15-second timeout, and accepts only the exact clean response. Infected, invalid, oversized, unknown and unavailable outcomes do not proceed through the app upload or extraction paths. No malware signature, file content or scanner response is logged by the client. This is a fail-closed integration point, not a complete quarantine or incident-response system.
